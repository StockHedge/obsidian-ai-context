## 승격 후보 ① — 패턴: API 계약을 바꾸면 "배포"가 한 세트다

- **경위**: PR #150 이 기프티콘 카탈로그 응답을 배열 → `{items, monthly_limit, …}` 객체로
  바꾸고 인증을 요구하게 했다. 백엔드는 main 푸시로 **자동 배포**됐지만 웹(Cloudflare Pages)은
  수동 배포다. 그 결과 라이브 번들(구계약)이 새 응답을 파싱하지 못해 교환소가
  **"등록된 기프티콘이 없습니다 / 보유 포인트 0P"** 로 보였다.
- **실측 정합**: 로컬에 남아 있던 구 번들(`dist/`)을 8081 로 서빙하고 **운영 API** 를 향하게 해
  같은 증상을 재현했다. 에러가 아니라 "빈 상태" 로 보이는 게 위험하다 — 콘솔 오류도 없다.
- **재사용 교훈(30-patterns 후보)**: ① 프런트/백엔드 배포 주기가 다른 저장소에서 **계약 변경
  PR 은 배포 순서를 PR 본문에 적는다**. ② 계약 변경은 한쪽만 배포돼도 안전하도록
  (구·신 양쪽 수용) 만들거나, 두 배포를 한 창구에서 묶는다. ③ "자동 배포되는 쪽"이 계약을
  먼저 바꾸면 파손 시간이 사람의 반응 속도만큼 길어진다.
- 이번엔 웹 배포 명령이 세션 권한 분류기에 막혀 실행하지 못했고, 우회하지 않고 인계로 남겼다.

  가 junction 을 따라가 main 의 `node_modules` 를 비운다(2026-09-02 실측)" 가 이미 적혀 있었다.
- 그런데 junction 존재 여부를 확인하는 PowerShell 한 줄의 **문자열 이스케이프가 깨져** 잘못된

  main 의 `node_modules` 가 비었고 `npm install`(14초, 707 패키지)로 복구했다.
- **재사용 교훈**: 파괴적 명령의 사전 확인 스크립트는 **복잡하게 쓰지 말 것**. 확인 자체가
  틀리면 가드가 아니라 잘못된 확신이 된다. "없음" 이라는 결과는 "확인에 실패했음" 과
  구분되지 않으므로, 파괴 전 확인은 긍정 신호(존재를 증명)로 설계하는 편이 안전하다.
