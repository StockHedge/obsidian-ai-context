# Play 데이터 안전성 답안 초안이 코드와 어긋나 있었다 — 제출 직전 발견

## 요약

Play Console 「데이터 보안」 설문을 채우려고 `docs/APP_STORE_SUBMISSION.md` 의 준비된
답안 표를 쓰려는 순간, 코드 재검증에서 **오류 3건**이 나왔다. 그대로 제출했으면
**허위 신고**였다. Play 는 "앱 콘텐츠에 대한 허위 진술이 있는 경우 앱 또는 앱 업데이트를
거부할 수 있다"고 설문 요약 화면에 명시한다.

## 무엇이 틀렸나

### 1. 전화번호 — 항목의 정체 자체가 달랐다 (가장 위험)

초안: `휴대폰 인증 / 근거 /api/auth/* / 목적 본인확인 / 선택 / 저장 안 함(해시만)`

실제:

- **앱에는 휴대폰 인증 화면도 엔드포인트 호출도 없다.** `/api/auth/phone/*` 는 웹 전용이고
  앱은 `me.phone_verified` 플래그만 표시한다.
- 앱이 실제로 평문 전송하는 번호는 **사이트 폼의 사업장 대표번호**(`phone`·`contact_phone`)다.
- 목적은 본인확인이 아니라 **앱 기능**이고, 음식점 유형에서는 **필수**다.
- 🔴 **"저장하지 않음(해시만)"이 결정적 허위였다.** 폼 값은 `pipeline_runs.form_data`
  JSONB 에 **평문 저장**되고 생성 HTML 에 실려 **공개 사이트로 배포**된다.
  `sanitize` 는 자유텍스트의 주민번호·카드번호만 마스킹한다.

즉 초안은 *웹의 본인확인 해시 저장*을 *앱의 폼 입력 평문 저장*으로 착각했다.
둘은 같은 "전화번호"라는 이름을 쓰지만 수집 주체·목적·보관 방식이 전부 다르다.

### 2. 근거 방향이 반대

이름·이메일·사용자 ID 의 근거를 `/api/users/me` 로 적었는데 그건 앱이 **받는** 응답이다.
앱이 올리는 것은 OAuth 인가 코드뿐이고, 이름·이메일은 백엔드가 provider 에서 직접 받는다
(`POST /api/auth/{provider}/callback` → `_upsert_user`).

### 3. 신고 항목 누락

폼 스키마에 `address`(음식점 필수)·`contact_email`(6개 유형 전부 필수)이 있다.
Play 는 자유 텍스트가 아니라 **"무엇을 받도록 만든 칸인가"** 로 판단하므로 별도 신고 대상이다.
초안은 이 둘을 "앱 활동 → 기타 사용자 생성 콘텐츠" 한 줄에 뭉뚱그렸다.

## 근본원인

문서가 **웹 기준으로 쓰였는데 심사 대상은 앱**이다. 두 표면이 같은 백엔드를 공유하고
용어(전화번호·이메일)가 겹쳐서, 웹에서 참인 문장이 앱 설문 답안으로 그대로 복사됐다.

작성 시점에는 근거로 엔드포인트 경로를 적어 뒀지만 **경로가 업로드인지 다운로드인지,
어느 클라이언트가 부르는지**를 확인하지 않았다. "근거 링크가 붙어 있다"가 "검증됐다"로
읽힌 것이 함정이다.

## 교훈

- **규제 신고 문서는 심사 대상 표면(앱/웹)을 명시하고, 그 표면의 코드로만 검증한다.**
  같은 백엔드를 공유해도 클라이언트가 다르면 답이 달라진다.
- **"어디에 저장되는가"까지 확인해야 한다.** 전송만 보고 "저장 안 함"을 쓰면 허위가 된다.
  이번 건은 평문 저장 + 공개 배포까지 이어져 있었다.
- 근거 표기는 **엔드포인트 + 방향(업로드/다운로드) + 호출 클라이언트**를 함께 적는다.
- 재검증은 **문서를 쓴 세션이 아닌 다른 컨텍스트**에서 코드로 돌려야 잡힌다.
  이번엔 병렬 조사 에이전트가 잡았다.

## 부수 발견 — 조사 프롬프트의 워크트리 함정

같은 조사에서 에이전트가 `docs/APP_STORE_SUBMISSION.md` 의 다른 항목 2건(`blockedPermissions`,
앱 내 계정삭제 진입점)을 **"허위 기재"로 보고**했다. 확인해 보니 그 변경은 미머지 브랜치
(`app/store-prep` worktree)에 있었고 에이전트는 지시대로 main 워크트리를 읽었을 뿐이다.

⚠️ **worktree 를 쓰는 저장소에서 조사 에이전트를 돌릴 때는 어느 워크트리·브랜치를 읽어야
하는지 프롬프트에 명시해야 한다.** 안 그러면 "문서가 거짓말한다"는 오탐이 나온다.
다만 그 오탐이 **진짜 문제 하나를 드러냈다** — main 에 머지된 문서가 main 코드에 없는
것을 "✅ 완료"로 적고 있었다. 문서와 코드는 같은 브랜치에서 함께 움직여야 한다.
