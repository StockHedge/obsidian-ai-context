# 2026-08-09 · P0 첫 실사용 생성 — 계측·크레딧 원장 실검증

메인 PC 복귀 세션. 두 달 가까이 "코드는 있는데 한 번도 안 돌아본" 상태였던
`pipeline_runs.metrics`(계측)와 `credit_ledger`(크레딧 원장)를 **실제 생성 2건으로 검증**했다.
덤으로 LLM 전환 판단의 전제였던 비용 구조가 숫자로 확정됐다.

## 왜 이게 P0 였나

`pipeline_run` 은 1건 있었지만 `stage_2`·`stage_3` 이 없고 생성~완료가 0.1초인 **합성 데이터**였다.
그래서 계측·원장은 **코드만 있고 한 번도 실행된 적이 없는 경로**였고, 둘 다 소급 복원이 불가능하다.
그리고 [[확정-결정]] §5 의 LLM 전환 판단이 "실측 0건이라 가정 위에 있다"는 이유로 **보류 중**이었다.

## 순서를 바꿨다 — 실험 전에 계기부터

바로 생성을 돌리려다 멈췄다. **`pipeline_runs.metrics` 를 읽는 코드가 backend 어디에도 없었다**
(콘솔 AI 비용조차 `cost_usd` 만 쓴다). 즉 순수 *쓰기 전용* 적재라 저장이 조용히 깨져도
화면상 증상이 없고, 관측 수단이 없으면 **단 한 번뿐인 첫 생성을 낭비**하게 된다.

대안은 Neon SQL Editor 직접 조회인데 그건 **2026-06-21 전체 wipe 사고가 난 바로 그 경로**다.
그래서 읽기 전용 CLI 를 먼저 만들어 배포했다(PR #114):

- `admin_cli.py metrics [run_id]` — 적재 여부·stages 수·`metrics_cost` vs `cost_usd`·스테이지 상세
- `admin_cli.py ledger <email>` — 원장 내역 + `sum(delta)` vs `preview_credits` 정합

판정 기준을 docstring·출력에 박아 넣었다. 아래 "죽은 필드"를 모르면 정상을 고장으로 오진한다.

## 결과 — 둘 다 정상

운영자 계정으로 실생성 2건(소상공인·Opus 경로·창의성 표준). 둘 다 `stages=4`,
`metrics_cost == cost_usd` **소수점 6자리 일치**, `stop_reason` 전부 `end_turn`(잘림 없음),
`prompt_ver`/`pricing_ver` 해시가 두 run 동일 → 해시 적재가 **안정적**임은 확인.
⚠️ 다만 *내용이 바뀌면 해시도 바뀐다*는 쪽은 **아직 관측하지 못했다**(무변경 상태의 2 run이라
판별 불가). 프롬프트를 고친 뒤 해시 변화 1회를 봐야 설계 검증이 끝난다.

| run | 총비용 | S3 출력 토큰 | 소요 |
|---|---|---|---|
| `85e999c1` | **$0.507** | 19,733 | 272초 |
| `7ecc1121` | **$0.534** | 22,510 | 293초 |

원장은 **1번째 무기록 → 2번째 `spend_generate −1,000`**(`balance_after`=25,000, 실제 잔액과 일치).

## 🔴 가장 값진 것: "정상"을 "고장"으로 오진할 뻔했다

첫 생성 뒤 원장이 **비어 있었다.** 그대로 봤으면 "원장이 안 돈다"고 결론냈을 것이다.

실제로는 **무료 1회 경로(`free_generation_used` 원자 클레임)가 `record_credit` 을 아예 호출하지
않는다**(`api/pipeline.py:678-687`). 크레딧이 실제로 차감되는 else 분기에서만 기록된다.
즉 **무료 퍼널 전 구간(가입 → 첫 생성 무료 → 첫 배포 0원)에서 원장이 비는 것이 정상 상태**다.

이 사실은 생성을 돌리기 *전에* 코드를 읽어 미리 예측해 뒀기 때문에 오진을 피했다.
관측 대상을 "첫 생성"이 아니라 **"차감이 실제로 일어나는 2번째 생성"** 으로 재정의한 것이 핵심.

교훈: **관측 결과가 비어 있을 때 "고장"과 "그 경로가 안 탔음"을 먼저 구분하라.**
분기 조건을 모르는 상태의 관측은 오진 생성기다.

## 비용 구조 확정 — [[확정-결정]] §5 의 전제가 바뀌었다

- **S3(코드 생성)가 비용의 약 76%**, S2(Opus) 약 20%, S1·S4(Haiku) 약 5%.
  외부 검토자의 *"입력이 작고 출력이 크다"* 주장이 **숫자로 확정**됐다(출력 20K 토큰대).
- 🔴 **캐시 적중 0** — 두 run 모두 전 스테이지 `cache_read = 0`. 원인은 **워크로드 특성으로 추정**
  (캐시 TTL 5분 내 재생성이 실운영에 거의 없음). ⚠️ **배선 불량 가능성은 아직 배제하지 못했다** —
  판별하려면 `metrics.stages[*].cache_write_tokens` 가 0 초과인지 봐야 한다(0이면 `cache_control`
  배선 결함 쪽). **미확인.** 게다가 cache write 는 입력 정가의 **1.25배** 과금이라, read=0·write>0 이면
  캐싱은 중립이 아니라 **순비용 증가**다.
  ⇒ 어느 쪽이든 결론은 같다: **비용 모델에서 캐싱 절감을 빼야 한다.**
- 저장소 문서에 있던 계산값 $0.60~0.70 은 실측보다 **약 20% 높았다**.
- 남은 미지수는 **Gemini 경로 실측 1건**뿐. 그것까지 받으면 전환 판단이 가능하다.

## 문서가 운영 코드와 모순돼 있었다

`CLAUDE.md` 에 **"Opus 금지 (비용 폭증)"** 이 규칙으로 남아 있었는데, Opus 는 이미
9,900원 동일가의 **사용자 선택 상품**이고 실측에서 S2 가 `claude-opus-4-8` 로 돌았다.
금지 대상은 *기본값을 조용히 상위 모델로 바꾸는 것*이지 사용자가 고른 경로가 아니다 — 정정했다
(코딩 규칙 절 + `절대 하지 말 것` 목록 **양쪽 다**. 한쪽만 고치면 강한 규범인 금지 목록이 이긴다).
⚠️ 같은 검증에서 **내가 새로 넣은 오기**도 잡혔다 — "gemini → S3 Sonnet" 이라 적었으나 S3 를
Sonnet 으로 내리는 분기는 **opus 전용**이고 gemini 경로는 S3 도 Gemini 다(`_stage_model`).
그대로 뒀으면 Gemini 실측 비교가 통째로 틀어졌다.
소요 표기도 "평균 100~200초"(Sonnet 시절) → **실측 272~293초**로 갱신.

## 부수 발견 (금전 영향 없음)

- **원장 추적성**: `spend_generate` 의 `ref_type`/`ref_id` 가 비어 어느 run 의 차감인지 역추적 불가.
- **계측 죽은 필드**(고장 아님, 코드 한계): S3 `actual_model` 항상 null(`LLMResult` 에 model 필드
  없음), 스테이지별 `latency_ms` 전부 null(호출부 미전달), `reasoning_tokens` 항상 0
  (Anthropic 은 `usage.output_tokens_details.thinking_tokens` 에 둔다).
- **Windows pytest 부작용**: `references/manifest.json` 을 CRLF 로 덮어써 542줄 유령 diff.
  백엔드 테스트 직후 되돌리지 않으면 노트북과 매 커밋 충돌한다.
- **브라우저 자동화**: React 제어 컴포넌트에서 체크박스·라디오는 값 설정이 아니라 **실제 클릭**이어야
  `onChange` 가 돈다. 텍스트 입력도 **병렬로 넣으면 리렌더와 경합해 뒤 항목이 조용히 유실**된다.
