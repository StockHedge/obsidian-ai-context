## 왜 9월 30일인가

지시는 "9월 31일" 이었으나 **9월은 30일까지**다. 인쇄물과 DB 양쪽에 들어가는 값이라
확정 전에 바로잡았다.

방향도 뒤집혔다. 처음엔 "만료를 앞당기면 인쇄된 포스터와 어긋난다" 고 볼 뻔했는데,
포스터에는 이미 **9/30 이 인쇄**돼 있었다. 즉 이건 만료 단축이 아니라
**인쇄물(9/30)과 DB(12-31)의 불일치를 DB 쪽으로 맞추는 정정**이다.

## 감사에서 나온 것

7개 에이전트로 코드·설정·테스트·문서 파급을 교차검증했다. 값진 발견 셋:

### 하마터면 호스팅 매출이 빠질 뻔했다

`promo_bundle_until` 키 하나가 번들 −4,000원과 **첫 달 전 티어 0원** 두 행사의 종료일을
겸한다. 날짜만 늘렸으면 0원 행사가 4개월 더 연장될 뻔했다 → [[프로모션-플래그-지도]]

### 시안 문구가 거짓이었다

"적립된 혜택은 …까지 쓸 수 있어요" 라고 썼는데, 적립분에는 **만료가 구현돼 있지 않다**.
만료가 막는 건 아직 등록 안 한 신규 가입자뿐 → 기존 사용자 **소급 영향 0**.
"코드 등록은 9/30까지, 적립 후에는 기한 없음" 으로 정정 → [[표기-주의사항]]

### 만료 후 유입이 무음으로 실패하고 있었다

`?promo=` 를 sessionStorage 에 담고 URL 에서 지우기만 해서, 포스터를 보고 들어온 사람이
화면에서 아무것도 못 봤다. 만료 뒤에는 에러조차 없이 혜택 0 으로 가입이 끝나고
결제 화면에서야 이상을 눈치채는 구조 — 회수 불가능한 인쇄물이 돌고 있어 반드시 생길 경로였다.

## 배포 후 해야 할 일

코드 배포만으로는 반영되지 않는다.

1. `PATCH /api/promo/admin/START2026?expires_at=2026-09-30T23:59:59%2B09:00`
   (DB 는 아직 12-31)
2. 콘솔 정책 탭 → `promo_bundle_until` = `2026-12-31`
   (**코드 기본값만 고치면 DB 행에 막힌다**)
3. 콘솔 정책 탭 → **`promo_first_month_free` OFF**
   (OFF 후에도 Basic 은 0원 유지. Plus 0→3,900 / Pro 0→10,900)
4. `GET /api/payments/hosting/plans` 로 `promo_until`·실제 `first_month` 대조
