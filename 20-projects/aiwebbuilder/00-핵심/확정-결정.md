### 왜 "사이트당"인가

총 9개월을 계정 카운터 하나로 주면 사이트를 3개 굴릴 때 **한 달에 3이 빠진다**(3개월 만에
소진). "사이트 3개를 각각 3개월"이라는 약속을 지키려면 개월 수를 **구독=사이트 단위**로
세야 한다. 그래서 두 축으로 쪼갰다:

- `User.promo_free_sites` — 무료 구독을 더 붙일 수 있는 **남은 사이트 수**
- `Subscription.free_months_remaining` — 그 사이트의 **남은 개월**

기존 `User.hosting_free_months`(운영자 레퍼럴)는 계정 단위 그대로 두고 **병존**한다.
소진 순서는 **캠페인 → 레퍼럴**이다(캠페인은 사이트를 접으면 함께 사라지는 소멸성 자원이라
먼저 태우는 쪽이 사용자에게 유리).

### 만료의 의미가 항목마다 다르다 — 광고 문구 주의

- **크레딧**: 🔴 **2026-08-01 정책 변경** — 마감일까지 미사용분은 **소멸**한다.
  (그 전까지는 만료가 없었다. 이 문장을 근거로 쓴 옛 안내가 남아 있다면 전부 정정 대상이다.)
  구현 완료·게이트 `promo_credit_expiry_enabled` **기본 OFF** — 고지가 충분히 노출된 뒤 켠다.
- **무료 호스팅**: `User.promo_free_hosting_until` 이후에 배포한 사이트에는 **안 붙는다**.
  코드를 등록만 해두고 11월에 만든 사이트는 대상이 아니다.

→ "적립 후에는 기한이 없어요"는 크레딧에만 참이다. 호스팅에 대고 쓰면 허위 표기가 된다.
자세한 건 [[표기-주의사항]].

### 무료 종료 후 타임라인

```
무료 소진 → [D-3 갱신 안내 SMS + 결제 링크] → 만료
  → 유예 3일 (사이트 살아 있음) → [유예 D-2 정지 예고 SMS] → 사이트 정지
```

결제 링크는 **로그인 없이 바로 결제**되며 유효기간 **7일**(서명 토큰).
로그인을 요구하면 문자를 받은 사람 대부분이 이탈한다는 판단.

## 4. 반복해서 데인 함정

### 실재하지 않는 날짜 → 무음 실패 (2026-07-31 실제 사고)

`promo_bundle_until` 에 **`2026-09-31`** 이 들어가 있었다. 9월은 30일까지다.

두 곳의 `except ValueError` 가 서로 다르게 처리해서, **화면은 "첫 달 0원"인데 실제로는
정가가 청구**됐다. 에러 로그도 없었다. 지금은 `app_settings` 쓰기 지점에서 날짜를 파싱해
막고, 콘솔 UI 는 `<input type="date">` 라 구조적으로 입력이 불가능하다.

교훈: **값을 바꾸기 전에 현재 값을 읽는다.** 이 버그는 그렇게 해서 발견됐다.

### 만료 시각은 naive UTC 로 저장된다

KST 로 끊으려면 `+09:00` 오프셋을 붙인다. 벽시계(`23:59:59`)를 그대로 넣으면 실제 만료가
**9시간 늦어진다**. `admin_cli.py promo --expires-kst` 는 이 변환을 알아서 한다.

### 광고 문구와 코드가 갈라진 전례가 반복된다

티어 표기, 만료 개념, 기한 하드코딩 — 세 번 다 코드를 확인하지 않고 문구를 먼저 냈다.
금전 혜택이라 분쟁 소지가 실질적이다. [[표기-주의사항]] 을 광고 전에 반드시 본다.

### 로그인 요구가 보이지 않는 곳에 숨어 있었다 (2026-08 코드리뷰)

갱신 결제는 **"로그인 없이 바로 결제"가 설계의 핵심**인데, 실제로는 100% 401 이었다.
엔드포인트에 인증을 건 적은 없다 — `rate_limit()` 이 내부적으로 `get_current_user` 에
의존해서, 핸들러에 닿기도 전에 막혔다. 비로그인 전용 변형 `rate_limit_anon()` 이 따로 있다.

이 버그의 성질이 중요하다. **로그인된 브라우저로 열면 멀쩡히 동작한다.** 개발자는 늘
로그인 상태라 수동 QA 로는 영원히 안 잡히고, 링크를 받는 사람은 전원 로그아웃 상태다.
그래서 `backend/tests/test_renewal_no_auth.py` 가 화면이 아니라 **의존성 트리 구조**를
검사한다(그 테스트가 실제로 탐지 능력이 있는지 증명하는 자기검사도 함께 둔다).

교훈: "인증을 안 걸었다"는 **인증이 없다는 뜻이 아니다.** 공용 의존성이 무엇을 끌고 오는지
확인한다.

### 곱한 값을 한 곳에서만 쓰면 나머지가 조용히 틀린다 (2026-08 코드리뷰)

연간 구독은 월 금액 × 10 을 청구하는데, **실제 청구는 맞고 `Payment` 기록만 1/10** 이었다.
환불 상한·영수증·매출 집계가 전부 1/10 로 어긋난다. 증상은 첫 연간 구독 **365일 뒤**에야
나타나서, 그때는 원인 코드를 아무도 기억하지 못한다.

교훈: 금액을 변형했으면 **그 값이 흘러가는 모든 기록 지점**을 따라간다. 청구가 맞다고
기록이 맞는 게 아니다.

## 6. 운영 반영 현황 (2026-08-09 실측 — 07-31 판을 갱신)

> 07-31 판에서 "🔴 프론트 구버전 · PR #112 머지 대기"였던 항목은 **해소됐다.**
> `pipeline_runs 0건`도 숫자가 바뀌었으나 **의미는 그대로**다(아래).

### ✅ 백엔드·프론트 모두 배포됐다

마이그레이션 head **`0048_promo_expiry_notified`** 운영 적용 확인.
`0044`(캠페인 무료 호스팅)·`0045`(계측)·`0046`(크레딧 원장)·`0048`(소멸 고지 시각).
갱신 결제 화면·연간 토글이 운영 번들에 들어갔다(PR #112 머지 완료).

운영 API 가 내려주는 캠페인 값(07-31 이후 변동 없음):

```json
{"credits":15000,"free_hosting_months":9,"free_hosting_sites":3,
 "free_hosting_months_per_site":3,"remaining_uses":997,
 "expires_at":"2026-09-30T14:59:59Z"}
```

`14:59:59Z` = KST 23:59:59. 총 9개월이 API 경계에서 곱해져 나온다(배너·팝업이 각자
곱하면 한 곳이 빠졌을 때 값이 갈리므로 서버가 정규화한다).

### 🟡 계측·원장은 코드만 있고 실검증되지 않았다

`pipeline_runs` 는 07-31 의 0건에서 **1건**이 됐지만, 그 1건은 `stage_2`·`stage_3` 이
없고 생성~완료가 **0.1초**인 **합성 데이터**다. 즉 **실제 사이트 생성은 여전히 0건**이고,
`pipeline_runs.metrics`(계측)와 `credit_ledger`(크레딧 원장)에는 **아직 아무것도 없다**.

두 값 모두 소급 복원이 불가능하다. **첫 실제 생성이 도는 순간이 이 코드의 첫 실행**이므로,
그때 값이 실제로 쌓이는지 확인해야 한다.

### 🔴 캠페인은 실제로 쓰이기 시작했다 — 다만 원장 이전이다

`used_count = 2/999`. 두 사용자 모두 `promo_free_sites=3` 이 정상 적립됐다.
**즉 코드 등록 → 적립까지는 실증됐다.** 아직 검증되지 않은 구간은 그 다음이다:
`subscription` 이 **0건**이라 *배포 → 무료 구독 자동 생성* 은 한 번도 돌지 않았다.

⚠️ 사용 시점이 2026-06-21 과 08-01 인데 **크레딧 원장 배포는 08-03** 이다. 그래서
`credit_ledger = 0` 이 **정상이고**, 그 2명의 적립 내역은 **영원히 원장에 없다**(소급 불가).
화면은 `tracking_since` 로 "이 시점부터 기록됩니다"를 알린다.
