### 1. R2 고아 이미지 교차 테넌트 삭제 (HIGH)

신규 `_r2_key_from_url`이 삭제 키를 `products/` 접두사와 `..` 부재로만 판정한다.
업로드는 `products/{tenant_id}/{uuid}.{ext}`인데 **삭제 판정에 그 테넌트 세그먼트 대조가 없다.**
`delete_images`는 `BackgroundTasks`라 DB 세션이 없어 RLS·`_scoped()`가 구조적으로 개입 불가하고,
`_delete_keys`는 플랫폼 자격증명으로 버킷 전체에 `delete_object`를 건다.

경로: 무료 가입 셀러가 게스트 API(`/api/market/search`)나 공개 PDP에서 타 테넌트의 R2 URL을
수집 → 자기 상품 `images`에 저장(`sanitize_image_urls`는 scheme·길이·금지문자만 검사) →
상품 삭제 → 백그라운드 회수가 **타 테넌트 객체를 영구 삭제**.

호출부 4곳 동일: `api/seller_products.py:348,376`, `seller_console.py:3701`,
`seller_ocr_phases.py:406`. 유일한 완화는 `r2_configured()` 게이트인데 이는 배포 상태이지
코드 통제가 아니다 — **자격증명 주입 시점이 곧 활성화 시점**이다.

신규 회귀 테스트(`test_storage_orphan.py`)도 외부 호스트·`..`·`other/`만 보고
교차 테넌트 케이스가 빠져 있었다.

### 2·3. 구세대 할인코드의 fail-open 쌍 (MEDIUM×2)

`_resolve_discount_code`가 1인당 한도를 `customer is not None`일 때만 검사하고(2),
총 발행 상한은 결제 확정 시점에만 증가하는 카운터를 읽어 pending 주문이 슬롯을
점유하지 않는다(3). 3번은 동시성이 필요 없는 **순차 재현**이라 이론적 레이스가 아니다.

핵심은 이것이 **저장소 자신의 확립된 계약에서 이탈**했다는 점이다 — 커밋 순서까지 확인됐다:

```
8858c25  fix(security) … 게스트 한도 쿠폰 거부(무제한 재사용 우회 차단)   ← 감사 지적 수정
   ↓
681271c  구세대 할인코드 경로 도입 (fail-open)                          ← 같은 결함 재도입
```

0064 혜택 엔진(`benefit_loader.reserve_benefits`)은 fail-closed를 올바르게 따랐다.
**세 형제 경로 중 할인코드만 단독 예외.**

### 4. 예약 조회 코드 엔트로피 (MEDIUM)

`R{yymmdd}-{token_hex(3)}` = 비밀 24비트. 접두는 생성일에서 유도 가능하고 조회 폼
placeholder가 형식을 노출한다. 생성기 docstring이 16.7M을 **충돌 예산**으로 서술하는데,
베어러 토큰에는 잘못된 분석이다(충돌 저항 ≠ 추측 저항).

선례가 이 설계를 지지하지 않는다 — 게스트 주문 조회는 64비트 + 회원 주문엔 로그인 게이트.
예약은 둘 다 낮췄다. `confirm_code`가 `String(32)`라 `token_hex(8)`까지 마이그레이션 없이 확장 가능.

⚠️ 최초 권고의 "로그인 세션 요구"는 스키마상 **적용 불가** — `ReservationBooking`에
`customer_id`가 없는 게스트 전용 레코드다. 실행 가능한 조치는 엔트로피 확장 단독.

### 5. 역할 회수 우회 (MEDIUM)

이 브랜치가 3단 역할 모델(`viewer < operator < superadmin`)을 도입했으나
`console.py`의 파괴적 뮤테이션 4종(테넌트 정지·활성화, 리뷰 승인·거부)이 이관되지 않았다.
`require_admin` 호출이 `console.py` 전체에 0건이고, 역할 부여 핸들러가 `viewer`에도
`is_admin=True`를 세우며 `is_operator()`는 `admin_role`을 보지 않는다.

`roles.py` docstring이 "파괴적 액션은 `require_min_role`로 추가 게이트"라고 **스스로 선언**하는데
그 4개만 누락됐다. 템플릿도 impersonate·flags만 superadmin 가드를 두고 정지·승인 폼엔 없다.

실제 시나리오는 "신규 최소권한 부여"가 아니라 **기존 운영자의 강등 = 불완전한 권한 회수**다
(부여 핸들러가 대상을 이미 운영자인 계정으로 제한하고, 앱에 `is_admin` 해제 라우트가 없어
강등이 유일한 권한 축소 수단이다). 리뷰 승인은 머니패스(승인당 무료 1개월).

## 시도했지만 실패한 접근 — 반증으로 탈락한 2건

오탐 방지가 실제로 작동한 사례라 남긴다.

**cron 시크릿의 JWT 키 폴백** (`config.py:164`) — 독립된 2에이전트가 각각 발견했으나
**둘 다 반증**(확신 3·2). 공격 1단계가 성립하지 않는다: 실제 스케줄러는 `CRON_SECRET`만
셸 변수로 전송하고 JWT_SECRET은 어느 경로로도 GH Secrets에 들어가지 않는다.
앱 내 유일한 아웃바운드 사용처는 superadmin+CSRF 게이트 뒤 자기 호스트 루프백.
→ 취약점 아님. **위생 항목**(폴백 제거 + `compare_digest` 통일)으로 백로그.

**Ops 앱 클릭재킹** (`ops/main.py:15`) — 헤더 누락은 사실이나 **프레임된 문서가 인증되지 않는다.**
세션·CSRF 쿠키 모두 `SameSite=Lax`이고 교차 출처 iframe은 최상위 내비게이션이 아니라
cross-site 하위리소스라 쿠키가 실리지 않는다 → 로그인 화면이 렌더된다.
게다가 `embolos-ops`는 prod 미배포. → 방어심층으로 헤더 추가는 권장하나 취약점 등급 아님.

**교훈**: "보안 헤더가 없다"와 "공격이 성립한다" 사이에는 브라우저 쿠키 정책이라는 층이 있다.
두 건 모두 식별 단계에서는 자신감 0.85였고, **반증 전용 렌즈가 붙어서야** 걸러졌다.

## 재발방지

1. **fail-closed 계약은 형제 경로 전수 확인과 함께 고친다.** 보안 수정 커밋에
   "같은 계약을 쓰는 다른 경로 N곳 확인" 항목을 넣는다. 이번 건은 쿠폰만 고치고
   할인코드를 놓친 것이 6개월 뒤 재도입으로 이어졌다.
2. **쓰기 경로에 테넌트 세그먼트가 있으면 삭제 경로에도 있어야 한다.**
   특히 `BackgroundTasks`는 DB 세션이 없어 RLS가 개입하지 못하므로
   테넌트 인자를 **등록 시점에 캡처**해 명시 전달해야 한다.
3. **역할·권한 모델을 새로 도입하면 기존 파괴적 라우트의 이관 목록을 함께 만든다.**
   라우터 레벨 fail-closed `Depends`가 있으면 신규 라우트의 회귀도 막힌다.
4. **베어러 토큰의 엔트로피 근거를 docstring에 "충돌"이 아니라 "추측 저항"으로 쓴다.**
   같은 저장소에 64비트 선례가 있는데 24비트로 내려간 것을 리뷰가 못 잡았다.
5. 회귀 테스트에 **교차 테넌트 케이스**를 기본 포함한다(경로 순회만 검증하면 이번 건이 통과한다).

## 다른 프로젝트에도 적용할 규칙

- **적대적 반증을 별도 렌즈로 분리하면 실제로 오탐이 걸러진다.** 이번에 2/7이 탈락했고,
  둘 다 식별 단계 확신도는 0.85였다. "확인해라"가 아니라 **"반증해라, 불확실하면 반증"**
  으로 프롬프트를 뒤집는 것이 핵심이었다.
- **git 이력 대조를 반증 렌즈의 필수 항목으로 넣는다.** "이 브랜치 신규분인가"를
  `git diff main...HEAD`로 확인하지 않으면 기존 부채를 신규 취약점으로 보고하게 된다.
- **다중 에이전트의 독립 중복 발견이 곧 참을 뜻하지 않는다.** cron 시크릿 건은
  2에이전트가 독립 발견했으나 둘 다 반증됐다. 교차 확증은 신호이지 증거가 아니다.
