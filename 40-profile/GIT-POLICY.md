# Git 운영 정책

## 개정 이유 (v4 → v5, 2026-08-13)

v3는 "작업 브랜치의 push는 확인 없이"로 권한을 넓혔다. 그러나 개인 dotfiles와 Vault는
작업 브랜치를 두지 않고 `main` 단일 브랜치로 운영된다. 이 저장소들에서는 v3의 완화가
한 번도 적용되지 않고 **모든 push가 보호 브랜치 확인 대상**이 되어, v3가 없애려던
"확인 대기 중 방치"가 그대로 남았다.

2026-08-13 실측: `claude-dotfiles`에 미푸시 5커밋 누적(`behind 0` / `ahead 5`).
직접 원인은 `_dotfiles/claude-sync.ps1`의 `push` 액션이 커밋할 새 변경이 없으면
`return`으로 빠져나가 `git push`에 도달하지 못한 것이었고(같은 날 수정), 구조적 원인은
1인 private 저장소에까지 보호 브랜치 규칙을 일률 적용한 것이다.

v5는 협업자·CI·배포가 붙지 않은 1인 private 저장소의 fast-forward push를 확인 대상에서
제외한다. force push 금지와 public 저장소 push 확인은 그대로 유지된다 — 완화의 근거는
"되돌릴 수 있는가"이지 "내 저장소인가"가 아니기 때문이다.

## 개정 이유 (v3 → v4, 2026-08-09)

Vault가 원격 저장소를 갖게 되면서 자동 커밋 주체가 둘이 될 수 있는 상태가 됐다.
Obsidian Git 플러그인과 Stop 훅 `git-autosync.ps1`이 같은 워킹트리에 붙으면 `index.lock`
경합과 편집 중 부분 커밋이 발생하고, 커밋 작성 주체를 사후에 구분할 수 없다.

v4는 「Vault 적용」 절에 **저장소별 자동화 소유권**을 명시한다. 이는 훅을 끄는 것이 아니라
어떤 저장소가 훅의 대상인지를 마커(`.git/autosync`)로 명확히 하는 것이며, 기존 v3의
opt-in 구조를 그대로 쓴다.

같은 날 두 기기의 Vault 저장소가 공통 조상에서 각각 8커밋씩 분기해 있던 사실도 확인됐다.
원인은 "사본이 두 벌 존재했고 어느 쪽이 기준인지 정해져 있지 않았던 것"이다.
기준 저장소를 하나로 두고 기기별 사본을 두지 않는다는 원칙을 [[VAULT-SYNC]]에 둔다.

## 개정 이유 (v2 → v3, 2026-07-29)

v2는 `push`·`pull`을 사용자 확인 대상으로 두었다. 실제 운영에서 사용자는 Git 명령을
직접 실행하지 않고 AI가 전담하므로, 이 규정은 "확인 대기 중 방치"로 귀결됐다.
2026-07-29 실측: 21개 저장소에 미푸시 커밋 50건 누적, 한 저장소는 원격보다 96커밋
뒤처짐, 전역 설정 저장소(`~/.claude`) 자체가 19일간 미커밋 상태.

동시에 확인된 사실은, 지시문만으로는 준수가 보장되지 않는다는 것이다.
CLAUDE.md에 규칙이 있던 저장소에서도 동일한 누락이 발생했다. 세션은 대체로
"정상 종료"되지 않으므로(창 닫기, 크래시, 컨텍스트 압축) 종료 시점에 건 규칙은
가장 필요한 순간에 실행되지 않는다.

따라서 v3은 두 가지를 바꾼다.
1. 일상적 Git 작업의 권한을 넓힌다 — 확인 대상을 되돌리기 어려운 작업으로 한정한다.
2. 준수를 지시에 맡기지 않고 **결정적 훅 계층**으로 강제한다.

## 기본 모델

- `main` 또는 기본 브랜치는 안정된 상태로 유지한다.
- 독립 작업은 `ai/<topic>` 또는 프로젝트 관례에 맞는 작업 브랜치에서 수행한다.
- 한 작업 폴더에는 한 AI만 쓰기를 수행한다.
- 병렬 작업은 별도 브랜치와 worktree를 사용한다.

## 보호 브랜치 정의

`main`, `master`, `release/*`, `prod`, `production` 을 보호 브랜치로 본다.
프로젝트가 별도 관례를 두면 프로젝트 문서가 우선한다.

## AI가 별도 확인 없이 할 수 있는 것

- `git status` · `git diff` · `git log` · `git branch --show-current` · `git fetch`
- 요청된 작업 범위 안에서 새 로컬 작업 브랜치 생성
- 테스트가 완료된 논리적 체크포인트의 로컬 커밋
- **작업 브랜치에서의 `git push`** (v3 신설)
  - 보호 브랜치가 아닐 것
  - 원격이 이미 설정돼 있을 것 (원격 생성은 여전히 확인 대상)
  - upstream이 없으면 `git push -u origin <현재 브랜치>` 까지 허용
- **작업 브랜치에서의 `git pull --rebase --autostash`** (v3 신설)
  - 보호 브랜치가 아니고, 충돌이 발생하지 않는 경우에 한한다
  - 충돌이 나면 즉시 중단하고 사용자에게 보고한다 (자동 해소 금지)
- **1인 private 저장소의 보호 브랜치 `push`·`pull --rebase`** (v5 신설)
  - 대상: 사용자 1인이 소유·사용하는 private 저장소로, 협업자·CI·배포 파이프라인이
    연결돼 있지 않은 것. 현재 해당: `StockHedge/claude-dotfiles`,
    `StockHedge/obsidian-ai-context`
  - 조건: `behind 0`인 **fast-forward**일 것. merge나 수동 rebase가 필요한 상태면
    확인 대상으로 되돌아간다
  - `--force` 계열은 이 예외에 포함되지 않는다 (아래 「절대 금지」 유지)
  - 저장소가 public으로 전환되거나 협업자가 추가되면 예외는 즉시 소멸한다
- **자동화 훅에 의한 WIP 커밋·푸시** — 아래 「자동화 계층」의 조건을 모두 만족할 때

브랜치나 커밋을 만들었다면 이름, 커밋 해시, 포함 파일을 사용자에게 보고한다.

## 사용자 확인이 필요한 것

- **보호 브랜치로의 `push`** — 위 「1인 private 저장소」 예외(v5)에 해당하면 제외
- 보호 브랜치에서의 `pull` — 위 예외에 해당하고 fast-forward면 제외
- 브랜치 병합 (`merge`)
- 대화형·수동 `rebase` (위 자동 `pull --rebase` 예외 제외)
- `cherry-pick`, `revert`
- 브랜치 또는 태그 삭제
- 릴리스·배포와 연결되는 Git 작업
- **원격 저장소 생성 또는 변경** (`gh repo create`, `git remote add/set-url`)
- **public 저장소로의 push** — 공개 범위 변경은 되돌릴 수 없다

## 금지

- force push (`--force`, `--force-with-lease` 포함)
- `reset --hard` 등 광범위한 변경 폐기
- 사용자나 다른 AI의 미커밋 변경을 임의로 포함하거나 삭제
- `.env`, 토큰, 키, 쿠키, 서비스 계정 파일 커밋
- 테스트 실패를 숨긴 커밋
- 자동화 훅에 의한 위 항목 전부 — 훅에도 동일하게 적용된다

## 자동화 계층 (v3 신설)

지시문은 프롬프트이고 훅은 강제다. 준수가 중요한 규칙은 훅으로 옮긴다.

### 적용 조건 (opt-in)

저장소 `.git/autosync` 파일이 존재할 때만 동작한다.
머신별 설정이며 저장소에 커밋되지 않는다. 파일을 지우면 그 저장소는 즉시 제외된다.

### Stop 훅 — 조건부 자동 커밋·푸시

Claude가 응답을 마칠 때마다 평가하되, 스로틀 간격(기본 600초) 이내면 건너뛴다.
세션이 어떻게 종료되든 최대 한 턴 분량만 유실된다.

다음 중 하나라도 해당하면 **아무 것도 하지 않는다**:

- git 저장소가 아님
- `.git/autosync` 마커 없음
- rebase / merge / cherry-pick 진행 중
- detached HEAD
- 보호 브랜치 (커밋까지만 허용, push는 하지 않음)
- 원격 없음 (커밋까지만 허용)
- 스테이징 후보에 비밀값 패턴이 검출됨 → 중단하고 사용자에게 경고
- **변경 파일 수가 한도(기본 40건)를 초과함 → 보류하고 경고** (`CLAUDE_AUTOSYNC_MAX_FILES`로 조정)
  - 근거: 2026-07-29 embolos에서 첫 실사용 발화가 256개 파일을 단일 WIP 커밋으로 묶어
    push했다. 비밀값·캐시는 없었고 유실도 없었으나, "생성된 230개 산출물이 저장소에
    속하는가"라는 판단이 세션 모르게 내려졌다. 대량 변경은 안전망이 아니라 결정이며,
    결정은 훅이 아니라 사용자 몫이다.

### SessionStart 훅 — 상태 주입

세션 시작 시 `git fetch` 후 브랜치·미커밋·ahead/behind를 컨텍스트에 주입한다.
"원격이 96커밋 앞서 있는 줄 몰랐다" 유형의 사고를 구조적으로 차단한다.

### 훅 실패 원칙

훅은 작업을 막지 않는다. 실패해도 항상 exit 0 하고 로그에만 남긴다.
로그: `~/.claude/logs/git-autosync.log`

## 충돌 시

1. 자동으로 한쪽을 선택하지 않는다.
2. 충돌 파일과 양쪽 변경 의도를 설명한다.
3. 사용자에게 선택이 필요한 부분을 보고한다.
4. 결정 후 병합하고 테스트한다.

`PROGRESS.md`·`NOW.md` 류의 인계 문서가 충돌하면 어느 한쪽을 버리지 않고 병합한다.

## Vault 적용

- 이 Vault는 `main` 브랜치의 Git 저장소로 관리한다.
- 정책·구조·승격 변경은 검증 후 커밋한다.
- 2026-08-09: 사용자 승인으로 GitHub Private 저장소 `StockHedge/obsidian-ai-context`에 연결했다.
  2026-07-29 점검에서 지적된 "이 PC 외에 사본이 없어 백업 부재가 단일 장애점"은 해소됐다.
- **자동화 소유권: 이 저장소의 자동 커밋·푸시는 Obsidian Git 플러그인이 단독으로 수행한다.**
  Vault 저장소에는 `.git/autosync` 마커를 만들지 않으며, 따라서 위 「자동화 계층」의 Stop 훅
  대상이 아니다. 같은 워킹트리에 자동 커밋 주체가 둘이면 `index.lock` 경합과 편집 중 부분
  커밋이 발생한다. Claude Code가 Vault를 편집할 때는 이 문서의 수동 커밋 규칙을 따른다.
- 원격 저장소의 추가 생성·변경(`gh repo create`, `git remote set-url`)은 계속 확인 대상이다.
- 기기 간 동기화 절차는 [[VAULT-SYNC]], 커밋 단위와 기준선은 [[VERSION-CONTROL]]을 따른다.

이 문서가 공통 Git 권한 정책의 기준이며 각 AI 전역 설정의 복사본보다 우선한다.
