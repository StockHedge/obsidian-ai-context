# "없다"고 적은 메모는 근거와 확인 위치를 함께 적는다

## 문제

인계 문서와 결함 대장에는 두 종류의 사실이 섞인다.

- **긍정형**: "이 엔드포인트는 X를 반환한다", "이 잡은 100분마다 돈다"
- **부정형**: "이 권한은 제공되지 않는다", "이 기능은 지원 안 한다", "우회 방법이 없다"

둘은 검증 비용과 수명이 완전히 다르다. 긍정형은 한 번 호출해 보면 확인되고, 틀리면
바로 드러난다. **부정형은 "어디를 봤는데 없었다"는 맥락이 없으면 재확인 자체가
불가능하다.** 어디를 봐야 하는지 모르니까.

그리고 부정형은 조용히 상한선이 된다. 다음 사람은 그것을 전제로 삼아 **그 경로를
시도조차 하지 않는다.** 틀린 긍정형은 실행하면 깨지지만, 틀린 부정형은 아무 일도
일어나지 않아서 틀렸다는 신호가 영원히 오지 않는다.

외부 플랫폼(Meta, Google, Slack)에서 특히 위험하다. 콘솔이 여러 겹이고 같은 개념이
여러 화면에 나뉘어 있어서, **한 화면에 없다는 것이 플랫폼에 없다는 뜻이 아니다.**

2026-08-11 실측(for-marketing): 결함 대장에 *"`instagram_basic`은 신형 앱 체계에서
제공되지 않는다(유스케이스 추가 불가 확인)"* 라고 적혀 있었다. 그 한 줄 때문에 7일간
권한 경로를 아예 시도하지 않았고, IG 발행이 막힌 원인을 "Graph 전파 지연"으로 오인한
채 매일 자동 회수를 기다렸다. 실제로는 앱 대시보드 → 이용 사례 → Instagram API →
권한 및 기능에 그 권한이 있었고 **버튼 두 번으로 추가됐다.**

오독의 출처는 Graph API **탐색기**의 권한 드롭다운이었다. 거기 없는 것은 사실이지만,
탐색기는 *앱에 이미 추가된* 권한만 보여준다 — 추가 가능한 목록이 아니다. 두 목록을
같은 것으로 본 것이 7일의 원인이다.

## 재사용 가능한 원칙

1. **부정형 사실에는 세 가지를 붙인다.** 어디서 확인했는지(정확한 화면·명령), 언제,
   무엇을 보고 그렇게 판단했는지. 셋 중 하나라도 없으면 다음 사람이 재확인할 수 없다.
   `~~취소선~~ + 정정 날짜`로 남기면 나중에 뒤집혔을 때 이력도 보존된다.

2. **"목록에 없다"와 "제공되지 않는다"를 구분해 적는다.** 전자는 관찰이고 후자는
   결론이다. 관찰만 적으면 다음 사람이 다른 화면을 볼 여지가 남지만, 결론을 적으면
   탐색이 거기서 끝난다.

3. **막혔을 때 가장 먼저 의심할 것은 부정형 메모다.** 다른 모든 가설을 시도한 뒤가
   아니라, 처음에. 비용이 낮고(콘솔 한 번 열기) 적중하면 전체가 풀린다.

4. **"자동으로 해소된다"도 부정형의 변종이다.** "지금은 안 되지만 기다리면 된다"는
   판단에는 **만료 기한**을 함께 적는다 — 언제까지 안 되면 고장으로 볼 것인지.
   → [[silent-field-omission-vs-propagation-delay]]

## 적용 조건

- 인계 문서·결함 대장·ADR에 "없다/안 된다/지원 안 함/불가능"을 적을 때 (**항상**)
- 외부 플랫폼 콘솔에서 무언가를 찾지 못했을 때 — 화면 이름을 함께 남긴다
- 특히 그 결론이 **후속 작업을 차단하는** 성격일 때
