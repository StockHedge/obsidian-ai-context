# 린터가 지운 import 는 "지금도 안 쓴다"가 아니다

## 문제

린터 자동수정(`ruff --fix`, `eslint --fix`)만 담은 브랜치가 오래 열려 있고,
그 사이 main 에 기능이 추가되면 같은 파일에서 충돌한다.

이때 "정리본(린터 브랜치)을 취한다"가 자연스러워 보이지만 위험하다.
**린터는 브랜치를 딴 시점 기준으로 미사용을 판단했다.** 그 후 main 에 들어온 코드가
지워진 심볼을 쓰고 있으면 런타임에 `NameError` / `ReferenceError` 가 된다.

실측(aiwebbuilder, 2026-08-17): 정리본에 `get_redis` 와 `rate_limit` 이 없었다.
린터 브랜치를 딴 뒤 main 에 들어온 세션 핸드오프 엔드포인트가 **두 이름을 모두 쓰고
있었다.** 정리본을 그대로 취했다면 배포 후 첫 호출에서 죽었다.

## 왜 테스트가 잡아주지 못할 수 있는가

- 새 기능의 테스트가 그 경로를 모킹하면 import 소실이 드러나지 않는다.
- 반대 방향 실수도 조용하다. Python 은 **중복 import 를 허용**한다 — 같은 파일에
  `logger` 정의가 두 번 있었고 그 뒤 import 가 전부 `E402` 였는데, 테스트는 전부 통과했다.
  즉 **이 영역의 오염은 테스트로 관측되지 않는다.**

## 재사용 가능한 원칙

- 린터 자동수정 브랜치의 충돌은 **헝크를 손으로 병합하지 않는다.**
  도구가 결정적이므로 **main 쪽을 통째로 취한 뒤 `--fix` 를 다시 돌리는 것**이 맞다.
  같은 입력에 같은 출력이 나오고, 손 병합에서 생기는 미묘한 실수가 없다.
  손으로 봐야 하는 것은 도구가 만들지 않은 부분뿐이다(워크플로 YAML·설정 핀·문서).
- 정리본에만 있거나 정리본에서만 사라진 심볼은 **사용처를 직접 grep 해서 판정**한다.
  "린터가 지웠으니 안 쓰는 것"이라는 추론을 하지 않는다 — 그 판단은 과거 시점의 것이다.
- 린터 전용 브랜치는 **짧게 살려 보낸다.** 오래 열어둘수록 충돌면이 넓어지고,
  넓어질수록 위 실수가 나올 확률이 올라간다.

## 확인 절차

1. 충돌 블록에 등장하는 모든 모듈·심볼을 나열한다.
2. 각 심볼이 **머지 결과 파일 전체**에서 쓰이는지 grep 한다. 충돌 블록만 보지 않는다.
3. 머지 후 린터를 다시 돌린다 — 새 코드가 들여온 신규 지적이 있다.
4. 전체 테스트 + **실제 엔드포인트 호출**로 확인한다. 타입체크만으로는 부족하다
   (동적 import·런타임 참조는 정적 검사를 통과한다).
