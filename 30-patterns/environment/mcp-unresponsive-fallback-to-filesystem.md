# MCP 서버가 무응답이면 파일시스템으로 우회한다

## 실측 (2026-08-09)

Obsidian MCP 서버의 **`list-available-vaults`** — 인자도 없고 목록만 돌려주는 가장 단순한
도구 — 가 **응답하지 않았다.** 120초 후 백그라운드로 밀렸고, **1800초(30분)** 까지 아무
응답도 진행 신호도 없이 중단됐다.

같은 세션에서 그 Vault 를 **파일시스템으로 직접 읽고 쓰는 것은 전부 정상**이었다.
노트 8건 갱신·신규 2건 작성·git 커밋까지 문제없이 끝났다.

⚠️ 이 세션 직전에 사용자는 "Obsidian MCP 정상 가동 중"이라고 알려줬다. **그 진술은
플러그인이 켜져 있다는 뜻이었지, 도구 호출이 응답한다는 뜻이 아니었다.** 연결 상태와
응답 능력은 별개다.

## 근본원인

**미확인.** 서버가 죽었는지, 요청을 받고 멈춘 건지, Vault 스캔이 오래 걸린 건지 구분할
근거가 없다 — 진행 신호가 전혀 없었기 때문에 "느림"과 "멈춤"을 구별할 수 없다.

## 재사용 가능한 원칙

- MCP 는 **편의 계층이지 유일한 경로가 아니다.** 대상이 로컬 파일이라면 파일시스템 접근이
  항상 존재하는 대안이다. 한 번 무응답이면 두 번째 시도 대신 **경로를 바꾼다.**
- 확인 비용이 싼 순서로 간다: 가장 단순한 도구(목록 조회 등)를 먼저 불러 **서버가 살아
  있는지부터** 본다. 무거운 호출로 시작하면 실패 원인이 서버인지 요청인지 섞인다.
- "연결됨"을 "동작함"으로 읽지 않는다. 사용자의 "켜져 있다"는 진술도 마찬가지다.
- 타임아웃 대기는 **작업을 막지 않게** 배치한다. 백그라운드로 돌리고 본 작업은 대안 경로로
  진행한다. 30분을 기다렸다면 그 세션은 아무것도 못 했을 것이다.
- 무응답 도구를 **재호출로 뚫으려 하지 않는다.** 같은 서버·같은 도구면 같은 결과다.

## 적용 조건

- MCP 서버가 로컬 리소스(파일·DB·Vault)를 감싸고 있어 **직접 접근 경로가 존재**할 때
- 도구 호출이 오래 걸리는데 진행 신호가 없을 때
- 세션 시작 시 MCP 가용성을 전제로 계획을 세우려 할 때

## 대응

- 즉시: 파일시스템(Read/Write/Glob/Grep)으로 전환하고 본 작업을 끝낸다.
- 설정으로 완화하려면 per-server `timeout`(ms) 또는 전역
  `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`(ms, 0 = 비활성). **다만 이건 무응답을 더 오래
  기다리게 할 뿐 고치는 게 아니다.**
- 원인 조사가 필요하면 서버 프로세스·플러그인 로그를 본다(이번 세션은 하지 않았다).
